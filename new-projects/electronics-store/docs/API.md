# Velmren Electronics API

All monetary values are integer RUB. Responses are direct JSON; errors `{error:string}`. Auth via Better Auth `/api/auth/sign-in/email` POST `{email,password}`, `/api/auth/sign-up/email` `{name,email,password}`, `/api/auth/sign-out` POST, `/api/auth/get-session` GET. Cookie sessions, same origin requests. Seed credentials are in local `.env` (`DEMO_PASSWORD`); buyer@velmren.local / admin@velmren.local. Never hardcode credentials into production.

- GET `/api/catalog?q=&category=&brand=&min=&max=&storage=&color=&inStock=true&sale=true&rating=&sort=popular|price-asc|price-desc|rating|new&page=1&limit=24` → `{products:Product[],total,page,pages,facets:{brands:string[],categories:Category[],colors:string[],storages:string[]}}`.
- GET `/api/products/:slug` → Product plus `reviews`, `questions`, `related`.
- Product shape `{id,slug,name,brand,category,subcategory,description,tagline,images:string[],specs:Record<string,string>,features:string[],inBox:string[],rating,reviewCount,featured,badge,modelUrl,videoUrl,variants:Variant[],selectedVariantId,price,oldPrice,stock}`. Variant `{id,sku,color,colorHex,storage,images:string[],price,oldPrice,stock}`. Category `{id,slug,name}`.
- GET `/api/cart` → `{id,items:[{id,variantId,quantity,variant,product,lineTotal}],subtotal,discount,shipping,total,promoCode,promoError}`. Cookie backed guest basket merged on next cart read after sign-in. POST `{variantId,quantity:1}` adds; PATCH `{variantId,quantity}` sets; DELETE `{variantId}` removes or `{}` clears. POST/PATCH may use `{promoCode:string}` to set promo. All return updated cart.
- GET `/api/favorites` → Product[]. POST `{productId}` adds, DELETE `{productId}` removes; authenticated.
- POST `/api/checkout` `{idempotencyKey:string,deliveryMethod:'courier'|'pickup',paymentMethod:'card'|'sbp'|'cash',address?:{name,phone,city,street,postalCode?},addressId?:string,promoCode?:string,comment?:string,useBonuses?:number,saveAddress?:boolean}` → Order. Accounts are optional; guests must supply contact details. Stock atomically reserved, own server prices used. Shipping 490 RUB courier / 0 pickup, free from 30000 RUB. Promo WELCOME10 takes 10%, maximum 5000 RUB. No real charging: explicit test payment step.
- GET `/api/orders` → Order[]. GET `/api/orders/:id` → Order. Order `{id,number,status,paymentStatus,paymentMethod,deliveryMethod,subtotal,discount,shipping,total,address,items:[{id,productId,variantId,name,slug,image,color,storage,price,quantity}],events:[{id,status,message,createdAt}],createdAt,trackingNumber,testMode}`.
- POST `/api/orders/:id/payment` `{result:'success'|'failure',eventId:string}` → Order. TEST_MODE only, authorized account or guest capability; staff may exercise provider events. Stable eventId idempotency. Failed payment may retry with a new eventId. POST `/api/orders/:id/cancel` `{}` → Order; stock returned once and test refund if paid. POST `/api/orders/:id/repeat` `{}` → current cart; validates current variant availability. POST `/api/orders/:id/shipping` `{}` advances a paid card/SBP order or a pending cash order through PROCESSING→SHIPPED→DELIVERED; cash becomes PAID on delivery in test mode only.
- GET `/api/profile` → user `{id,name,email,phone,role,bonuses,settings,addresses}`. PATCH `{name?,phone?,settings?:{newsletter?,sms?,emailNotifications?}}` → user. BetterAuth change-password endpoint handles password updates.
- GET `/api/addresses` → Address[]. POST `{name,phone,city,street,postalCode?,isDefault?}` → Address. PATCH same + `id`; DELETE `{id}` → `{ok:true}`.
- GET `/api/reviews?productId=` → approved Review[]. POST `{productId,rating:1..5,title,text}` → pending review, authenticated. Review `{id,userId,author,rating,title,text,status,isDemo,createdAt}`.
- GET `/api/questions?productId=` → approved Question[]. POST `{productId,text}` → pending question; authenticated. Question `{id,author,text,answer,status,createdAt}`.
- GET `/api/support` → own Ticket[]. POST `{subject,message}` → Ticket; authenticated. PATCH `{id,message}` appends own reply. Ticket includes `messages:[{text,staff,createdAt}]`.
- POST `/api/subscribe` `{email}` → `{ok:true}`. Idempotent DB persistence.
- `/api/admin/:resource` resources `products`, `variants`, `categories`, `brands`, `promos`, `orders`, `reviews`, `questions`, `support`, `users`, `dashboard`. STAFF/ADMIN read/manage content; only ADMIN deletes and changes users roles. GET → array (dashboard → `{products,orders,customers,revenue,pendingReviews}`); POST creates resource using its fields, PATCH `{id,...fields}`, DELETE `{id}`. Product create/update fields match Product excluding computed `price,stock,rating,reviewCount`; variants managed separately. Orders PATCH `{id,status}` enforces allowed transition. Reviews PATCH `{id,status:'APPROVED'|'REJECTED'}`. Questions PATCH `{id,answer,status}`. Support PATCH `{id,status?,message?}`. Users PATCH `{id,role}` ADMIN only.
- POST `/api/admin/upload` multipart `file` (JPEG/PNG/WebP, max 5 MB, signature validated) → `{url}`. Staff authorized; stored in S3/MinIO public images bucket.

Order states: PENDING_PAYMENT, PROCESSING, SHIPPED, DELIVERED, CANCELLED. Payment: PENDING, PAID, FAILED, REFUNDED. Payment and delivery provider implementations run in backend TEST_MODE; normal storefront controls omit simulation tools. Promos `{id,code,type:'PERCENT'|'FIXED',value,maxDiscount,minSubtotal,active,expiresAt}`.

Checkout also accepts `contact:{name,email,phone}`, `recipient:{name,phone}`, `pickupPoint:string`; these are persisted inside `Order.address`. Profile fields whitelist prevents roles and bonuses being changed by customers. Demo reviews are explicitly marked `isDemo:true`; catalog ratings are computed from approved DB reviews. Categories scope catalog facets. Numeric query values outside valid ranges return 400.

Verification: `npx vitest run tests/server` runs PostgreSQL integration tests against this dedicated local instance only. Seed: `npm run db:generate`, `npm run db:migrate`, `npm run db:seed`. PostgreSQL16 and MinIO images are pinned in compose; all service ports bind localhost. `.env.example` contains development-only credentials; replace before deployment. No live payment gateway configured.

Official implementation references: [Better Auth Prisma adapter](https://better-auth.com/docs/adapters/prisma), [Better Auth Next.js integration](https://better-auth.com/docs/integrations/next), [Prisma 7 PostgreSQL driver/configuration](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql). Auth signup requires a password of at least 10 characters.

## Reviewed contract corrections

- `PATCH /api/admin/variants`: when `stock` is supplied, `expectedStock` (the value originally read by the editor) is required. Missing/invalid expectedStock → 400; changed stock → 409 and no supplied fields are written. Example `{id,stock:12,expectedStock:10}`. Patches without stock do not need this field.
- Product responses now include `selectedVariantId`; selected variant is first in `variants`. Product-level `price`, `oldPrice`, and `stock` describe that exact variant. Catalog selection matches all variant filters; price sorting uses its price. Other variants remain available for selection.
- Guest cart merge carries its promoCode into an account basket only when the account has no code. Calculation revalidates it. Cart response adds `promoError:string|null`; an invalid/expired code gives zero discount and a message, and checkout refuses it until removed or corrected.
- Checkout adds `saveAddress?:boolean` (default false). A submitted address is saved in the checkout transaction only if requested and not already present for the same user/name/phone/city/street. Checkout replay and failure do not create extra addresses.
- Cash checkout starts `PROCESSING/PENDING`. Cash can transition to `SHIPPED` while payment is pending; `DELIVERED` atomically records `PAID` and awards bonuses once. Card/SBP require paid status before shipping. `/payment` is not required for cash.
- `src/server/providers.ts` defines `PaymentProvider` and `ShippingProvider`, typed payment success/failure/repeated results, and test implementations used by commerce services. External live implementations and verified provider webhooks remain integration work; no real money or shipping is performed.



## Guest checkout and catalog images

- `POST /api/checkout` accepts anonymous callers. `contact:{name,email,phone}` is required for guests. `address`, recipient, pickup point, comment and contact are persisted in the immutable order snapshot. Guest bonuses/addressId are rejected; `saveAddress` applies only to accounts.
- `GET/POST /api/cart` initializes a separate `ve-orders` cookie with 32 cryptographically random bytes. It is HttpOnly, SameSite=Lax, Secure on HTTPS, path `/`, one-year lifetime. Only its SHA-256 hash is stored with guest orders. The cart cookie alone never grants order access. Keep cookies on all checkout/order requests; identifiers and email alone grant no access.
- `GET /api/orders` lists only the caller's account orders or capability-scoped guest orders. Read/payment/cancel/repeat routes accept the same guest capability. Guest responses include `isGuest:true`. Internal `guestAccessHash` and `checkoutScope` are omitted. Payment defaults omitted `result` to `success`; stable `eventId` remains required. The provider still requires backend `TEST_MODE=true` and does not perform live charging.
- `GET /api/guest-checkout` returns `{contact:{name,email,phone}|null}` from the most recent unclaimed order scoped to that browser capability, for signup prefill. No email/address lookup is accepted.
- On an authenticated store API request, orders may be claimed only when their unclaimed guest capability matches this cookie AND their normalized contact email matches the authenticated account. Claims atomically set userId and revoke guest access. An existing account or a newly registered account works; email matching without cookie possession never claims anything. The auth UI makes this request immediately after signup/login. Bonus accrual applies only while an order belongs to an authenticated account; previously delivered guest orders receive no retroactive bonuses.
- Guest checkout/payment/cancel preserve database transactions and stock/idempotency guarantees. `checkoutScope` is stable even after claiming; its `(checkoutScope,idempotencyKey)` key isolates guest sessions and authenticated customers. Delivery simulation `/api/orders/:id/shipping` is staff-only. The storefront exposes payment/retry and cancellation, without simulation/failure/delivery tools.
- `Product.subcategory` defaults to `""`; `Variant.images` defaults to `[]`. Admin product/variant create and patch support both. `GET /api/catalog` accepts `subcategory=` and returns `facets.subcategories`. `productView.images` uses selected variant images, falling back to product images. Order snapshots use the chosen variant's first image. Approved reviews flagged `isDemo` are excluded from public review lists and public product rating/count calculations.


## Retired variants

`Variant.active` defaults to `true`; admin create/PATCH accepts `active:boolean`. Set false to retire an unverified/discontinued offer without deleting its row, changing its inventory, or altering historical order snapshots. Public product variants, selected price/stock/images, catalog facets and related offers exclude inactive variants. Catalog omits products with no active offers; their direct product page can still return an empty variants array and stock 0.

Cart POST/PATCH, checkout and repeat reject retired variants with 409. Existing cart rows remain removable and include `availabilityError:string|null` explaining unavailable/retired stock. Authenticated guest-cart merge skips retired variants. Checkout stock reservation also requires `active:true` atomically, preventing a concurrent retirement from being purchased. Historical orders and cancellation stock returns remain intact.


Claiming guest orders also preserves their entered account data in the same transaction: a blank profile phone is filled verbatim from the newest matching claimed contact; a nonempty phone is preserved. Valid courier addresses are copied into the account address book and deduplicated by user/name/phone/city/street. Only the first saved address becomes default; existing defaults are preserved. Pickup-point addresses are not copied. Order contact and recipient snapshots remain unchanged. User/guest locks serialize repeated and concurrent claims, preventing duplicate address entries.
